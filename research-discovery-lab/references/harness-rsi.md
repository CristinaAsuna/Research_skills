# Harness 自我改进（RSI）

harness 指引导 agent 工作的一切：`AGENTS.md`、`CLAUDE.md`、`lab.toml`、`templates/`、`tools/`，以及上游的这个 skill。RSI 的意思是让这些东西根据真实使用中的证据持续变好，同时不膨胀。

## 原则

- **只提案**：agent 写提案，用户批准后才应用。
- **证据驱动**：每个提案都要引用某个 topic 中实际发生的事，例如返工、歧义、遗漏、误读、超预算；不能基于想象中的问题。
- **减法优先**：先考虑修改或删除已有规则，再考虑新增。新增一条时，要说明它替代或合并了哪条。
- **容量是硬约束**：AGENTS.md 的行数上限见 lab.toml；超限时必须先删再加。
- **可追溯**：AGENTS.md 里的每条规则都带 `[H-xxx]`，指向 HARNESS_LOG 中的来源。

## 摩擦信号（每个 topic 复盘时收集）

| 信号 | 典型原因 | 可能的改进 |
| --- | --- | --- |
| 计划缺陷导致返工 | PLAN 缺图规格、对照或数据细节 | 调整 PLAN 模板字段或 Planner 规则 |
| 执行偏差 | PLAN 有歧义，或预算不现实 | 调整模板或 lab.toml 预算 |
| 超预算 | toy 层级选错，规模过大 | 调整 toy 规则或预算 |
| check 失败或误报 | 规则不清，或 check 过严 | 修改规则或 lab.py |
| 用户反复跳过某类问题 | 问题不合适或时机不对 | 修改问题库 |
| Reviewer 修正 SUMMARY | 执行者误读图或夸大结论 | 加读图或结论强度约定 |
| 同一问题第二次出现 | 缺少规则 | 写成规则 |

**提案门槛**：一次性事故先记在 REFLECTION 的 Harness 复盘里。同类问题第二次出现，或者一次就导致结论错误，才写提案。

## 提案格式（写在 HARNESS_LOG.md 的"待批提案"下）

```markdown
### H-012 一句话标题
- 来源：topics/<id>；证据：具体发生了什么（引用文件、提交或 check 输出）
- 改动：文件 + 改动摘要，写到 diff 级别；说明替代或删除了哪条规则
- 预期效果 / 代价：……
- 复查方式：之后 2 个 topic 中看哪个信号
```

## 应用与复查

1. 用户批准后修改对应文件，在 AGENTS.md 的规则末尾标 `[H-012]`，提交 `harness: H-012 …`。
2. 把提案移到"已采纳"表，复查期为之后 2 个 topic 的复盘。
3. 复查时看信号是否减少、是否带来了新摩擦，结论三选一：
   - **保留**；
   - **修订**：用新编号提案；
   - **撤销**：恢复原文，移到"已撤销 / 拒绝"。

## Retro（每 5 个已复盘的 topic 一次）

- 汇总摩擦指标和预测校准的趋势。
- 列出 AGENTS.md 中 5 个 topic 内从未触发过的规则，提议删除或合并。
- 检查容量上限；模板中总是填"无"的字段提议删除。
- 挑出与本工作区无关、对其他工作区也成立的改进，作为上游候选。
- 结果写进 HARNESS_LOG 的"Retro 记录"。

## 上游到 skill

- **条件**：改进已采纳并通过复查，而且对其他工作区同样成立。
- **做法**：
  1. 在 skill 仓库（`lab.toml [skill].path`）修改对应的 references、assets 或 scripts，并运行 skill 的测试。
  2. 工作区用 `lab.py init <root> --upgrade` 查看差异。
  3. 由用户决定是否同步。
- 不要把工作区特有的路径、偏好或 topic 细节写进 skill。

## 反模式

- **规则膨胀**：每次出事就加一条规则。
- **对单次事故过拟合**：为一个极端情况改动通用流程。
- **静默修改**：未经批准就改规则、模板、预算或 check。
- **事后合理化**：把没有证据表明有效的"最佳实践"写成规则。
- **指标游戏**：为了让 check 通过而删掉内容或写空话；为了提高命中率而只做容易预测的 topic。
