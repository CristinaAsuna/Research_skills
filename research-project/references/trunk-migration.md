# 主干迁移

主干是项目里唯一被当作基准的那条流程：一个 commit、一份配置、一个评测集、一个数。迁移只有两种情况。两种情况都按顺序做，每一步做完告诉用户结果，再做下一步。

## 情况一：把旧项目搬进模板

旧项目通常有这些问题：主干没有写明、代码没有全部进 git、评测脚本有好几个、文档很长而且过期、产物很多。迁移的目标是带走一条能复现的主干和几页结论，其余留在原地。不要试图先把旧项目整理干净。

### 第 1 步：冻结旧项目

- 在旧项目里把代码现状原样提交，包括未跟踪的源码、配置、脚本和测试，然后打 tag `legacy-<日期>`。
- 提交前检查 `.gitignore`，确认数据、权重、缓存和密钥不会被提交。
- 之后旧项目只读。不删除、不移动、不清理其中任何文件。
- 完成标志：`git status` 里没有未跟踪的代码；tag 存在。

### 第 2 步：先写 STATE.md，再搬代码

在新仓库运行 `scripts/project.py init`，然后和用户一起填 STATE.md 的"当前主干"：

- 哪一个结果是主干。选**已经验证过、数值最好、能说清配置和 checkpoint** 的那个，不选最新的那个。
- 它的配置文件、checkpoint 位置、评测集、主指标数值、必须对比的基线数值。

写不出来时停止迁移。这说明旧项目里没有可信的主干，第一件事是回到旧项目复现一个数。

### 第 3 步：只搬主干的依赖闭包

- 从主干的训练入口和评测入口出发，列出它们实际 import 到的文件。适合交给一个只读的 subagent 去做，让它返回文件清单。
- 只搬清单里的文件到 `src/<pkg>/`，配置搬到 `configs/trunk.yaml`。
- 转发壳、兼容层、已删除配置的引用都不搬。
- 评测脚本只搬一个，写进 docs/PIPELINE.md。
- 把清单给用户看过再搬。清单之外的代码一律留在旧项目。

### 第 4 步：在新仓库复现主干的数

- 用旧 checkpoint 在新仓库跑评测，得到的数要和 STATE.md 里的数一致。容差事先写明，例如相对误差小于 1%。
- 对不上就查原因，查清之前不做任何新实验。
- 对上之后，把评测集、指标定义和基线数值写进 docs/PIPELINE.md。

### 第 5 步：知识只搬结论

- 旧项目的评测记录、决策记录、状态文档，由 subagent 读完后提炼：
  - 仍然成立的结论，每条一行，写进 docs/PROJECT.md 的"已有结论"，标 `[历史]`。
  - 试过并放弃的方向，每条一行，写进"已排除的方向"。
  - 值得保留的实验，在 EXPERIMENTS.md 各记一行，"卡片"一栏写旧项目里的路径。
  - 数据契约写进 docs/DATA.md，只写一处。
- 不搬日记、结果大表、作业记录和待办清单。需要时回旧项目查。

### 第 6 步：登记资产

- 列出新仓库需要的数据集、checkpoint 和缓存，把机器和路径登记到研究工作区的 MACHINES.md 资产表。只登记，不复制大文件。
- 其余产物留在旧项目。可以另外给用户一份"可回收空间"的清单，由用户逐项决定是否删除。

### 第 7 步：侧线变成卡片

- 旧项目里还在进行的方向，各写一张 spike 卡片，写明停止门槛，放进 STATE.md 的排队。
- 卡片开始执行时才搬相关代码，并且搬进 `src/` 的开关或 `scratch/`，不照搬旧的目录结构。

### 第 8 步：锁定

- `tools/project.py check` 无 ERROR。
- 提交并打 tag `trunk-v1`，把 tag 和 commit 填进 STATE.md。
- 在 docs/DECISIONS.md 记 D-001：主干是什么，为什么选它，旧项目的位置和 legacy tag。

## 情况二：某个实验取代主干

### 条件

写在卡片里，并且在运行之前写好：

- 用同一个评测入口和评测集。
- 主指标超过主干多少算赢。差距要大于 seed 之间的波动。
- 至少几个 seed。单个 seed 的结果只够开一张确认用的卡片，不够取代主干。

### 步骤

1. 用户确认条件已满足。
2. 把 `configs/exp/<id>.yaml` 合并进 `configs/trunk.yaml`，实验用的开关改成默认行为，删除因此不再需要的旧代码路径。
3. 运行测试和评测，确认合并后的主干复现了实验的数。
4. 提交 `trunk: <一句话>`，打 tag `trunk-v<N>`。
5. 改写 STATE.md 的"当前主干"。
6. 在 docs/DECISIONS.md 记一条：新旧主干的数值、依据的实验 id。
7. 在 EXPERIMENTS.md 里：
   - 旧主干保留为一行基线，写明它的 tag。
   - 基于旧主干、尚未完成的实验，要么在新主干上重做，要么把状态改为 stale。
   - 已完成的旧实验不改数字，结论仍然是相对旧主干的结论。

### 更换评测集或主指标

这也是一次主干迁移，因为所有旧数字都不再可比：

1. 先在 docs/DECISIONS.md 记下原因。
2. 用新评测重新评一次主干，更新 STATE.md 的主指标。
3. 需要继续对比的旧实验，用新评测重评；其余标为 stale。

## 迁移中不要做的事

- 一边迁移一边改进方法。迁移只改变代码的位置，不改变数字。
- 因为"以后可能有用"把旧项目整个复制过来。
- 在旧项目和新仓库里同时继续开发。第 1 步之后，新工作只在新仓库里进行。
- 没有复现主干的数，就开始新的实验。
